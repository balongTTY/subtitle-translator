## 一、QThread 安全清理（HIGH — #44/#47）

**问题**：取消/超时强制销毁仍在运行的 QThread（worker 阻塞在最长 120s 的 LLM API 调用中时最常命中），触发 Qt 硬崩溃 `QThread: Destroyed while thread is still running`；facade 被 GC/替换后线程引用提前释放，同样崩溃。

**修复**（`core/translator.py`）：

1. **模块级线程注册表**（L28-32 `_live_threads`）：`prepare_translation` 登记每个 `(QThread, worker)` 作为外部强引用，`finished` 信号触发 `_cleanup_finished_thread`（L35-50，从注册表移除 + `deleteLater`）后才回收。即使 facade 被 GC，运行中的线程仍由注册表兜底持有。
2. **`_force_cleanup`**（L568-598）：先 `worker.cancel()` 设置取消事件 → `requestInterruption()` + `quit()` → `wait(3000)` 等待自然结束 → 最后才 clear 列表。引用由注册表持有，**绝不提前 clear**。
3. **`run()` 结束必须 quit**（L112-116）：`run()` 作为 `started` 的槽执行，返回后线程会进入 `exec()` 事件循环永久阻塞，finally 中必须 `QThread.currentThread().quit()`，否则线程泄漏 + 退出崩溃。
4. 清理路径不 connect `deleteLater`（L445-446），线程生命周期统一由 facade 拥有，避免二次释放。

**验收**：PyQt5 5.15.11 实机三条路径（cancel / del facade+gc / 正常完成）全部无崩溃、注册表正确清空。

## 二、LLM 编号解析修复（HIGH — #45/#46，LOW — #50）

**问题**：翻译提示词要求 LLM 按 `N. 译文` 编号行输出（输入编号从 0 开始），但 LLM 偶发从 1 开始重编号，整批键偏移 +1 导致 primary 范围整体错位一条，且旧逻辑**击穿质检**——错位后的译文恰落在条目数上一致时 QC 静默放行。

**修复**（`services/prompt_builder.py` `parse_response`，L264-309）：

1. **1 起始编号检测与对齐**：解析全部编号行后，若键中无 `0`、`min(translated) == 1`，且按「整体左移一档」对齐后在 primary 范围的命中数不少于原样对齐（打平时要求 `len(translated) >= len(batch.entries)` 防误伤 0 起始缺首条情形），则整体左移一档。同时覆盖首个批次与 overlap 批次（`primary_start_idx > 0`，1 起始重编号时 `min key == 1`）。
2. **未编号续行累积**（#50）：LLM 对多行源条目输出真实换行时，非编号行若不匹配格式噪声 `_NOISE_LINE_RE`（L14，匹配 ``` ~~~ > # --- *** ___ 围栏/分隔线/标题），则追加到前一条译文（join 用空格，与提示词规则一致），避免译文被截断为第一行。
3. 兼容输入编号变体 `N. / N、 / N: / N） / N) / N）`（`NUMBERED_LINE_RE`，L12）。

**验收**：`'1.译文0/2.译文1/3.译文2'`→`[译文0,译文1,译文2]`；overlap 批（primary 5..10）1 起始正确对齐；0 起始镜像/缺首条 tie 不左移；`'0.a\n1.b\nc\n2.d\n3.e'`→`[a,'b c',d,e]`；既有 test_parser 5 变体无回归。

## 三、Claude Prompt Caching 说明（MEDIUM — #58）

**问题**：原实现在**整个 system prompt** 上打 `cache_control` 标记。而 `## 当前场景 / 强制术语 / AI 建议术语 / 预设参考术语` 等批级内容随批次、glossary、QC 重试逐批漂移，前缀精确匹配永远不命中——缓存零收益、反而多付 1.25x 缓存写入费。

**修复**（`services/claude_service.py`）：

1. **拆两段发送**：`_split_cached_prompt`（L188-203）按行扫描，取第一个批级可变区段标题（`_BATCH_VARIABLE_SECTION_RE`，L22-24）为切点，把 system prompt 无损拆成「跨批恒定前缀」+「批级可变内容」。
2. `translate_batch`（L95-100）构造 `system_blocks = [恒定部分 + cache_control: ephemeral, 可变部分无 cache]`。
3. **分析阶段不缓存**（L130-132）：分析的 system 块是固定短句（约 14 token），远低于 1024 token 最小可缓存前缀，`cache_control` 会被 API 静默忽略，标记无意义。

**验收**：恒定前缀跨批字节级一致且 ja→zh 实测约 1359 token（>1024，缓存生效）；en→zh <1024（中性，不误判）。

> 使用者注意：README 中 Claude 一栏标注「Prompt Caching ✓ 需标记」——本工具内部已按上述方式标记，无需用户干预。

## 四、加密密钥注意（MEDIUM — #52，LOW — #68）

**问题**：非 Windows 兜底加密密钥原由「MAC 地址 + 源码硬编码盐」派生——两个输入都半公开，本地进程可轻易还原；且在无硬件地址环境下 `uuid.getnode()` 回退为每进程随机值，重启后密钥漂移、已存 `keys.enc` 无法解密。

**修复**（`config/settings.py`）：

1. **持久化随机密钥**（`_get_legacy_fernet`，L133-160）：非 Windows 环境从用户数据目录读取/生成 32 字节 `os.urandom` 密钥（`fernet.key`，读回校验长度 32、`chmod 0600`；缺失时经 tmp+chmod+`os.replace` 原子落盘）。**密钥文件本身即秘密**，重启后稳定。
2. **MAC 派生密钥降级为只读**（`_legacy_mac_fernet`，L122-130）：仅用于读取更早版本的历史 `keys.enc`，不再用于新写入。
3. **明文 `.keyfile` 无条件清理**（`_load_keys`，L186-194）：启动时放在方法最前、独立 try/except，`unlink` 失败仅告警、绝不影响密钥加载；迁移分支内原先脆弱的 `legacy_keyfile.unlink()`（会在抛错时清空 keys）已移除。
4. Windows 端保持不变：DPAPI（`CryptProtectData`，当前用户作用域，L81-119）加密 `%APPDATA%/SubtitleTranslator/keys.enc`，绑定当前用户账户。

**使用注意**：
- Windows 用户：换机器/换用户无法解开 `keys.enc`，属 DPAPI 预期行为。
- 非 Windows 用户：`fernet.key` 与 `keys.enc` 需**一起备份/一起迁移**，只拷 `keys.enc` 无法解密。
- 解密失败时写日志告警、原文件保留、keys 清空——不再静默丢数据，重新输入即可。

## 五、语料库路径问题（MEDIUM — #54，LOW — #75×2）

**问题（#54）**：PyInstaller 单文件打包环境下，`__file__` 指向只读的 `_MEIPASS` 临时目录，语料库写入后重启即丢失。

**修复**（`core/corpus_manager.py`）：

1. **`_resolve_corpus_path`**（L31-55）：`sys.frozen` 时写入 `%APPDATA%/SubtitleTranslator/corpus_vtuber.json`（与 settings 的 `_get_data_dir` 同模式），首次运行从打包内 `_MEIPASS/resources` 复制初始 json；非打包路径不变（`resources/corpus_vtuber.json`）。
2. **类级缓存 `_terms_cache`**（L23、L57-77）：跨实例复用语料库内容（analyzer/prompt_builder 每批新建实例）；所有写路径 add/remove/update_all 均经 `_save()` 落盘并同步缓存，缓存必然失效/更新。
3. **模块级签名缓存**（#75，`services/prompt_builder.py` L16-42）：`_get_corpus()` 以文件 `(st_mtime_ns, st_size)` 为签名，未变更时复用同一实例、变更后重建；路径解析复用 `CorpusManager._resolve_corpus_path()`（含旧版无该方法时的 `resources` 目录回退）。

**使用注意**：
- 源码运行：语料库仍位于 `resources/corpus_vtuber.json`。
- 打包运行：语料库迁移到 `%APPDATA%/SubtitleTranslator/`，首次启动自动从打包内复制初始内容；用户对术语库的编辑在打包版中持久生效。
